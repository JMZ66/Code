# 招投标文件审查助手使用说明

本工具在你的电脑上阅读 DOCX、PDF 和 XLSX，写出审查报告。它不修改这些原文件，不上传，也不连接云端模型。

## 1. 准备文件

准备：

1. 一份作为格式依据的 Word 模板（`.docx`）。模板里实际使用的样式、页边距、页眉页脚、编号和表头，就是格式检查的依据。模板没写的项目，工具不会用“通用公文格式”去补。
2. 要审查的正文、预算表、技术文件、合同和附件。支持 `.docx`、`.pdf`、`.xlsx`。
3. 可选的规则文件 `rules.json`。只有你写进去的外部依据、效力顺序和同义词才会被使用。

建议用清单，路径相对清单文件所在目录：

```json
{
  "template": "00_投标文件格式模板.docx",
  "conforming": ["02_投标文件格式响应.docx"],
  "rules": "rules.json",
  "documents": [
    {"path": "01_招标文件.docx", "role": "tender", "title": "招标文件"},
    {"path": "03_采购清单及预算.xlsx", "role": "budget", "title": "采购清单及预算"},
    {"path": "04_合同条款.docx", "role": "contract"},
    {"path": "05_技术标准和要求.docx", "role": "technical"},
    {"path": "07_附件_营业执照.pdf", "role": "attachment", "title": "营业执照"}
  ]
}
```

`conforming` 里的文件才会按模板核对版式和章节。预算表、合同正文不要放进去，除非它们确实要求套用同一模板。

角色用于和文件里的“效力顺序”对齐，常用值：

`tender`、`budget`、`technical`、`procurement`、`contract`、`attachment`、`conforming`、`other`

## 2. 图形界面

安装 Python 3.10 或以上后：

```bash
python -m pip install -r requirements.txt
python -m bidreview
```

Windows 便携版解压整个文件夹后双击 `BidReview.exe`。会同时打开一个控制台窗口，便于看到错误；不要只拷贝 exe。

界面中：

1. 选择模板 DOCX。
2. 选择一个空的输出目录。不要把输出目录设成某个原文件。
3. 添加 DOCX / PDF / XLSX，并为每个文件选择角色。需要套模板的文件选中后点“设为套用模板”。
4. 如需核对某个标准编号是否出现在包内，可在“外部依据”填写，例如 `GB/T 50314`。这里只检查包内有没有这个编号，不判断是否符合该标准。
5. 点“开始审查”。日志里会列出前若干条问题，完整内容在输出目录。

## 3. 命令行

```bash
python -m bidreview check --manifest 清单.json --out 审查输出
python -m bidreview check --template 模板.docx --file tender=招标文件.docx --file budget=预算.xlsx --conforming 投标格式.docx --out 审查输出
python -m bidreview hash 招标文件.docx 预算.xlsx
python -m bidreview self-test
```

`self-test` 只在临时目录写几份小文件，不读取你的标书。

## 4. 规则文件

```json
{
  "external_basis": [
    {"title": "GB/T 50314 智能建筑设计标准"}
  ],
  "precedence": ["投标人须知前附表", "合同专用条款", "技术标准和要求"],
  "subject_aliases": [
    {"family": "duration", "canonical": "总工期", "labels": ["考核工期"]}
  ]
}
```

- 不写 `precedence` 时，工具只采用正文里“效力顺序”或“优先顺序”后面的编号列表。
- 内置只把“总工期 / 计划工期 / 计划总工期”视为同一事项，把“预算合计金额”视为“预算合计”。供货期、服务期、主体施工工期、考核工期不会自动并到总工期。
- `subject_aliases` 是你明确要求合并时才生效。

## 5. 报告

输出目录包含：

| 文件 | 内容 |
| --- | --- |
| `审查报告.xlsx` | 问题、完整性、文档索引、抽取字段 |
| `审查报告.html` | 可单独打开的报告，不引用外网字体或脚本 |
| `审查报告.md` | 一览表和逐条原文 |
| `findings.json` | 机器可读结果 |
| `index.json` | 章节、段落、表格、页码索引 |
| `integrity.json` | 每个原文件审查前后的 SHA-256 |

问题表列：序号、类别、严重程度、规则、问题、原文、文件名、章节、结构位置、PDF页码、判定依据、建议。

四类的含义：

- **确定错误**：主体、条件和单位能对齐，数值或要求仍然冲突；或模板、占位、缺失、修订有直接证据。
- **疑似冲突**：出现“约”“左右”等不确定说法，数值不同，但不能定性为错误。
- **需要人工判断**：单位不能折算（例如月和日历天），或 PDF 没有文本层。
- **缺少依据**：你点名的标准或文件不在包内。工具没有内置条文，不能判断符不符合。

严重程度只是类别的固定映射：确定错误为高，疑似冲突和需要人工判断为中，缺少依据为低。

## 6. 工具不会做的事

- 不保存、不另存、不覆盖原始 Word、PDF、Excel。打开方式是压缩包只读、工作簿只读或 PDF 只读。审查结束后再次计算 SHA-256，报告里写出是否一致。
- 不把修订里已删除或尚未接受的文字当成现行数值。修订和批注会单独列出来。
- 不因为两个数字不一样就报冲突。上限未超过、分项合计与总工期一致、千米与米换算后相等、一个名称包含另一个名称，都不报。
- 不填写【待填写】、下划线或空单元格。
- 不计算 Excel 公式。单元格里如果只有公式、没有存好的数值，报告里看到的是公式文本。
- 不对扫描 PDF 做 OCR，因此没有文本层的 PDF 会交给人工。
- 不计算 DOCX 排版后的页码。DOCX 的位置是 `word/document.xml` 里的段落、表格、行和列。

## 7. 看一条工期冲突时怎么读

报告会同时给出两处或几处原文、各自的文件和章节、结构位置。如果正文写了效力顺序，判定依据会引用那段原文，并说明哪一处排在前面。它不会把排在前面的文字自动写回其他文件。

## 8. 重新生成练习用样本

样本是虚构项目，可用下面的命令写到一个新目录，再用清单审查：

```bash
python -c "from tests.corpus_builder import build_corpus; from pathlib import Path; build_corpus(Path('examples/sample'))"
python -m bidreview check --manifest examples/sample/manifest.json --out examples/sample-out
```

生成样本需要额外安装 `requirements-dev.txt`（python-docx 与 reportlab）。审查本身不需要它们。
